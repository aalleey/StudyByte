# Deploying StudyByte (Vercel + Render)

The frontend (static React/Vite build) goes to **Vercel**. The backend (Express API) and
**Postgres** both go to **Render**. These are separate accounts/dashboards - this guide walks
through both, in order, because the backend needs to exist before the frontend can point at it,
and the backend needs the frontend's URL for CORS once that exists too (you'll circle back once).

Total cost to start: **$0** on both platforms' free tiers. Check current free-tier limits/plan
names on each dashboard when you sign up - they do change over time.

---

## 1. Push the code to GitHub

Already done if you're reading this from the repo. If you're starting fresh elsewhere:

```bash
git init
git add .
git commit -m "Initial commit"
git branch -M main
git remote add origin https://github.com/<you>/<repo>.git
git push -u origin main
```

## 2. Backend + database on Render

1. Go to [dashboard.render.com](https://dashboard.render.com) and sign in (GitHub login is
   easiest - it also handles repo access).
2. **New -> Blueprint**, pick this repo. Render reads `render.yaml` at the repo root and proposes:
   - a Postgres database (`studybyte-db`)
   - a web service (`studybyte-api`) with its build/start/pre-deploy commands already set, rooted
     at `backend/`
3. On the review screen:
   - `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` are auto-generated by Render (`generateValue:
     true` in the blueprint) - you don't need to type anything for those.
   - `FRONTEND_URL` is left blank for now (`sync: false`) - leave it blank and apply; you'll set
     it in step 4 once the Vercel URL exists.
4. Click **Apply**. Render provisions the database, then builds and deploys the API. The
   `preDeployCommand` (`npm run db:deploy`, i.e. `prisma migrate deploy`) runs automatically
   before each deploy goes live, so the schema is always in sync.
5. Once live, note the service's public URL - looks like `https://studybyte-api.onrender.com`.
   Confirm it's actually up:
   ```bash
   curl https://studybyte-api.onrender.com/health
   # {"success":true,"data":{"status":"ok"}}
   ```
6. **Seed the database once** (admin/student/superadmin accounts + sample content). Render's
   Shell tab (web service -> Shell, available on paid instance types - the free tier may not
   include it) lets you run:
   ```bash
   npm run prisma:seed
   ```
   If your plan doesn't have Shell access, run it from your own machine instead, pointed at the
   production database: copy `DATABASE_URL` from the Render Postgres dashboard
   (Environment tab) into a one-off local `.env` value, then run `npx prisma db seed` from
   `backend/` locally. Don't commit that production `DATABASE_URL` anywhere.

> No free Shell access and don't want to expose the prod `DATABASE_URL` locally even briefly?
> Temporarily add `&& npm run prisma:seed` to the end of `preDeployCommand` in `render.yaml`,
> push, let it deploy once, then remove it and push again - `prisma db seed` runs your
> `prisma/seed.ts`, which is upsert-based and safe to run more than once.

## 3. Frontend on Vercel

1. Go to [vercel.com/new](https://vercel.com/new) and sign in (GitHub login again).
2. Import this repo.
3. On the configure screen:
   - **Root Directory**: `frontend` (this is the important monorepo setting - Vercel otherwise
     tries to build from the repo root)
   - Framework preset: Vercel auto-detects **Vite** once the root directory is set
   - **Environment Variables**: add
     ```
     VITE_API_URL = https://studybyte-api.onrender.com/api/v1
     ```
     (use your actual Render URL from step 2.5, with `/api/v1` appended)
4. Click **Deploy**. Once done, note the Vercel URL - looks like
   `https://studybyte.vercel.app` (or a `-xxxx.vercel.app` preview alias; use the production one).

---

## 4. Close the loop: tell the backend about the frontend

1. Back in the Render dashboard, open the `studybyte-api` service -> **Environment**.
2. Set `FRONTEND_URL` to your real Vercel URL, e.g. `https://studybyte.vercel.app` (no trailing
   slash).
3. Save - Render redeploys the service automatically with the new value.

This matters for two things: CORS (the API only accepts credentialed requests from exactly this
origin) and the link embedded in forgot-password emails.

---

## 5. Verify end to end

Open the Vercel URL in a browser:

- Log in as the seeded superadmin (`ali.khaliq50@gmail.com` / `laptop321`, or whatever you set
  during seeding) - confirm the admin dashboard loads and the view switcher works.
- Log in as the seeded student (`student@computer.local` / `Student@123`) - confirm the grade
  picker appears, pick a grade, confirm Notes loads.
- Refresh the page on a deep link like `/student/notes` - confirms the Vercel SPA rewrite
  (`frontend/vercel.json`) is working and you don't get a 404.
- Leave the tab open ~16 minutes (longer than the 15-minute access token lifetime) and perform an
  action - confirms the cross-domain refresh-token cookie (`sameSite: 'none'` in production) is
  actually being sent and the silent refresh works.

## Notes on the free tiers

- **Render free web services spin down after inactivity** and take ~30-60s to wake on the next
  request - the first request after idle will be slow, not broken. Upgrade to a paid instance
  type to avoid this for a real classroom.
- **Render free Postgres** may be a time-limited trial depending on your account/region - check
  the current terms when you provision it. If it expires, you'll need to upgrade the database
  plan or migrate to another Postgres host (Neon and Supabase both have generous free tiers and
  work as a drop-in `DATABASE_URL` replacement).
- Rotate `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` if they're ever exposed (e.g. accidentally
  committed) - this immediately invalidates all existing sessions, which is the correct response.
